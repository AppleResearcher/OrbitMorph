## 建议采用的统一模型

1. **源码库统一入口**：今后的新项目统一放在 ~/AgentLibrary/projects/<仓库名>，各项目独立 Git、独立 AGENTS.md、独立 README 和文档、测试与发布过程。
2. **运行目录与源码目录解耦**：Docker 服务暂时留在 ~/Docker；以后新服务应明确区分源码仓库、compose/运行配置、持久化数据。不要将持久化数据库、密钥或安装产物放入 Git。
3. **旧项目先建索引，再分期迁移**：在中心索引中记录现有位置、仓库、用途、负责人、运行状态、端口/反代是否有关联、迁移风险；已部署项目优先标记保留原位，不做物理移动。
4. **分支与命名**：main 是稳定，dev 是开发集成，feature/* 和 fix/* 仅用于有独立验收价值的改动；保留项目自身的上游贡献习惯，不强迫一次性调整所有旧项目。
5. **跨设备协同**：mini 为主开发/运行节点；MBA 和 lspc 可各自克隆 Git 仓库，依赖 GitHub 同步，非源码运行资产不跨机散发。
6. **集中只读目录**：~/AgentLibrary/projects/PROJECT_CATALOG.md 作为项目清单入口；未来如需历史追踪，可将索引独立纳入一个治理仓库，但不要把整个 projects 根目录初始化为 Git 仓库（避免嵌套仓库混淆）。

## 已有项目迁移的准入检查

- 核对 origin/upstream 与未提交的工作区变更，先完成备份。
- 确认 Docker Compose 的 bind mounts、卷挂载、系统服务、launchd、脚本路径和自动任务。
- 核对外部入口（NPM、域名、端口、回调）和跨设备依赖。
- 制定新旧路径兼容方案、停机窗口与回滚方法，完成逐项验证再决定是否迁移。
- 多数线上服务**不一定需要迁移**：有统一索引、统一 Git、统一运维与文档标准，就已经能够实现逻辑上的规范化。
